# T9-02 — План миграции “Offline → Mini‑Web → полноценный кабинет”

## Цель
Сформировать **конкретную** дорожную карту, риски и критерии go/no-go для перехода:

1) **Offline (CLI/скрипты) →**
2) **Mini‑Web (тонкая веб‑оболочка + джобы) →**
3) **Полноценный кабинет (RBAC, Audit, Alerts/Tasks, Observability)**.

Критический принцип архитектуры:

- `offline-core` (src/genomeai): **вся логика, ML, пайплайны, версии артефактов**.
- `web-cabinet` (web_cabinet): **ничего не считает**, только вызывает offline-core и показывает артефакты.

## Что остаётся общим
Единый контракт артефактов (сквозные версии):

- `data_version`
- `qc_run`
- `model_version`
- `scoring_run`
- `report_version`
- `decision_log`

и единый формат переносимости:

- **Pilot Pack**: zip, содержащий `versions.json` + (опц.) `pack_manifest.json` + слои `{canonical,qc,models,scoring,reports,decisions,metadata}`.

## Дорожная карта

### Этап 0 — Offline (текущее MVP)
**Что делаем:**
- Генерация артефактов в `artifacts/<data_version>/...`
- Сборка Pilot Pack: `genomeai pack`
- Проверка переносимости: `genomeai import-pack` в чистое хранилище

**Что не делаем:**
- Никаких долговременных “онлайн‑расчётов” в вебе.
- Никаких внешних зависимостей мониторинга (Prometheus/Grafana) в MVP+.

**Выход/критерии:**
- CLI пайплайн воспроизводим.
- Pilot Pack переносится и открывается в целевом layout.

### Этап 1 — Mini‑Web
**Смысл:** дать оператору интерфейс “загрузить → запустить джобу → скачать результат”, без сложной авторизации.

**Что меняется:**
- Добавляется `web_cabinet` с базовыми страницами и worker.
- Веб запускает offline-core через subprocess с таймаутами.
- Артефакты хранятся на диске локально (on‑prem).

**Что остаётся:**
- Форматы артефактов неизменны.
- Сквозные версии остаются единственными ID.

**Выход/критерии:**
- `healthz/readyz/metrics` доступны.
- Веб показывает списки `data_version`, `qc_run`, `model_version`, ...
- Джобы завершаются с логами и кодом возврата.

### Этап 2 — Полноценный кабинет
**Смысл:** multi‑role кабинет с управлением алертами/тасками, аудитом действий, расширенной наблюдаемостью.

**Что добавляется:**
- RBAC (Director/Zootech/Vet/Operator/Viewer) и audit log.
- Alert Center v2 + Tasks v1.
- “Decision Log” как append‑only.
- Наблюдаемость: метрики пайплайнов, алерты по падениям джобов.

**Что не делаем на этом этапе (явно):**
- Мульти‑инстансы (HA/кластер) без необходимости.
- Переезд на внешний DWH/облачное хранилище по умолчанию.

**Выход/критерии:**
- Политики доступа и аудит покрывают критические действия.
- Наблюдаемость достаточна для SLA.

## Риски и план совместимости

### Риски
- **Дрейф схемы артефактов**: новые поля/файлы ломают UI.
- **Потеря связности версий** (в pack отсутствует ключ или слои неполные).
- **Переполнение диска** (хранение слоёв + pack + бэкапы).
- **Конкурентные записи** (параллельные джобы пишут в один `data_version`).
- **Безопасность**: секреты, доступ к диску, перенос zip.

### План совместимости
- Переносимость делаем через **Pilot Pack**.
- `versions.json` — обязательный минимальный контракт.
- `pack_manifest.json` — опционально; если есть — включаем проверку sha256.
- При изменении структуры — добавляем новую схему (`...v2`) и держим импортёр backward‑compatible.
