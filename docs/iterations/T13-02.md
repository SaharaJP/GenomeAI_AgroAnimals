# T13-02 — Connectors framework: FileConnector + API/1C stubs + schedule

## Scope completed

1. Added config-driven connector framework with registry-by-kind and no need to change ingestion core for every new connector.
2. Implemented `file` connector with folder/path selection, config validation, incremental pull by source file hash, and canonical writes through existing offline-core ingest logic.
3. Added `api_stub` and `onec_stub` connector types with clear `stub` lifecycle status and operator-facing messages.
4. Added cron-like scheduler tick and connector journal tables in Web Cabinet DB.
5. Added minimal Web Cabinet page `/connectors` for configured connectors, manual run, schedule tick, and journal visibility.
6. Added automated tests for increment logic, scheduler enqueue/dedup, and Web Cabinet visibility.

## Additional scope completed (step 2)

7. Added FileConnector upload staging in Web Cabinet: operators can upload source CSV files directly into connector inbox/source_dir without changing offline-core.
8. Added connector detail page with current source snapshot, last pulled file metadata, and per-dataset upload actions.
9. Added automated Web tests for upload -> run -> canonical output flow and audit coverage for connector uploads.

## Additional scope completed (step 3)

10. Added connector run detail page `/connectors/runs/{connector_run_id}` with selected files, ingest summaries, increment reason, and manifest download link when available.
11. Added per-connector status summary on detail page: latest success / noop / stub / failure with direct links to run details.
12. Extended connector journal and connector detail tables with links for drill-down into specific connector runs.
13. Added automated Web tests for success/noop/failure visibility and manifest download from UI.

## Additional scope completed (step 4)

14. Added Web Cabinet connector editor: create new connector and edit existing connector config without manual YAML edits.
15. Added UI-level save flow with audit log `connector.config_save`, human-readable validation errors, and config persistence to `configs/connectors/*.yaml`.
16. Added connector health summary on catalog/detail pages: config validity, required bindings readiness, and upcoming scheduled slots.
17. Added automated Web tests for UI create/edit flow, execution of UI-created connector, disable flow, and validation-error visibility.

## Step 9 — partial dataset failures + retry failed bindings only

Что добавлено:
- `connector run` теперь умеет завершаться статусом `partial`, если часть dataset bindings успешно записана, а часть упала;
- manifest/run detail теперь содержат `dataset_results` с per-dataset статусами `written/failed/not_written_noop` и текстом ошибки;
- состояние коннектора обновляется только по успешно записанным dataset bindings, без потери прошлого baseline для неуспешных наборов;
- на странице `connector run detail` добавлена кнопка `Retry failed datasets only`, которая ставит в очередь повтор только для упавших dataset bindings;
- CLI и job enqueue поддерживают `--datasets animals,lactations` для subset-run/recovery;
- схема `connector_runs` расширена до статуса `partial` с online-migration для существующих БД.

Проверка:
- `pytest -q tests/web/test_t13_02_connectors_step10_partial_retry.py`
- UI: `/connectors/runs/<connector_run_id>` → `Retry failed datasets only`.


## Step 10 — connector-level recovery queue + auto retry for failed dataset subset

Что добавлено:
- на detail-странице коннектора появилась batch recovery UX-кнопка `Retry last failed datasets`, которая ставит в очередь повтор только последнего неуспешного subset-а без повторного запуска уже успешных bindings;
- добавлен блок `Recovery queue` на detail-странице: видны отложенные/queued recovery jobs, `next_attempt_at`, `trigger_type`, dataset subset и retry attempt;
- введена config-driven `retry_policy` в YAML коннектора: `auto_retry_failed_datasets`, `max_attempts`, `backoff_sec`, `retry_on_statuses`;
- CLI/job enqueue поддерживают lineage-поля `retry_parent_run_id` и `retry_attempt_no`;
- при `partial/failed` run можно автоматически поставить subset retry только для failed dataset bindings, без повторного прогона всего connector run;
- на странице run detail теперь видно, был ли auto retry запланирован или пропущен и почему.

Проверка:
- `pytest -q tests/test_t13_02_connectors_step1.py tests/web/test_t13_02_connectors_step7_force_and_slot.py tests/web/test_t13_02_connectors_step11_recovery_queue.py`
- UI: `/connectors/<connector_id>` → `Retry last failed datasets` / `Recovery queue`; `/connectors/runs/<connector_run_id>` → `Auto retry scheduled`.


## Step 11 — retry policy in UI + recovery queue guardrails + recovery analytics

Что добавлено:
- UI-редактор коннектора теперь умеет редактировать `retry_policy` без ручной правки YAML: `enabled`, `max_attempts`, `backoff_sec`, `retry_on_statuses` (`partial` / `failed`);
- dry-run preview теперь показывает активную retry policy рядом с preview-результатом;
- subset recovery run из UI теперь передает `retry_parent_run_id`, чтобы recovery lineage был прозрачен в аналитике и журналах;
- для recovery queue добавлены guardrails: запрещается ставить дубль subset recovery для того же connector + dataset subset + parent run, а также действует лимит queued recovery jobs на коннектор (`GENOMEAI_CONNECTOR_RECOVERY_QUEUE_LIMIT`, default=5);
- на detail-странице коннектора добавлен блок `Recovery analytics`: pending jobs/datasets, retryable runs, manual/auto recovery runs, recovered successes, success rate, queue limit и last recovery run.

Проверка:
- `pytest -q tests/web/test_t13_02_connectors_step12_retry_policy_guardrails.py`
- UI: `/connectors/<connector_id>/edit` → блок `Retry policy`; `/connectors/<connector_id>` → `Recovery analytics` и защита от duplicate recovery enqueue.


## Step 12 — recovery queue cancel/clear + last recovery decision

Что добавлено:
- на detail-странице коннектора появилась ручная отмена queued recovery jobs: cancel по одной записи и clear/cancel all для всей recovery queue;
- для отмен recovery jobs пишется audit (`connector.recovery_cancel`, `connector.recovery_clear`);
- на detail-странице коннектора теперь показывается `Last recovery decision` с человекочитаемой причиной (`auto retry disabled`, `max attempts`, `queue guardrail`, `status not retryable`, `scheduled`);

- recovery queue после cancel/clear сразу освобождает guardrails для нового subset retry.
